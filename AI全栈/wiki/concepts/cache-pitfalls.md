# 缓存雪崩、击穿、穿透

> 缓存失效导致请求全部打到数据库的三种典型故障模式，区别在**失效的原因和范围**：大批 key 同时失效（雪崩）、单个热点失效（击穿）、数据根本不存在（穿透）。

## 核心要点

- 判别口径：雪崩/击穿时**数据库里有数据**，缓存恢复即自愈；穿透是**缓存和库里都没有**，无法靠重建缓存解决。
- 击穿是雪崩的子集（单个热点 key 的"雪崩"）。
- 三者共同兜底思路：**让数据库永远只承受"可控流量"**——限流/熔断是最后防线，方案设计是第一防线。
- 穿透的治本是**布隆过滤器**：说"不存在"就一定不存在（单向无漏报），说"存在"可能误判。

## 细节

### 对照表

| | 雪崩 | 击穿 | 穿透 |
|---|---|---|---|
| 诱因 | 大量 key 同时过期 / Redis 宕机 | 热点 key 过期 | 查询不存在的数据（误删或恶意攻击） |
| 数据库里有数据吗 | 有 | 有 | **没有** |
| 解法方向 | 打散过期 + 高可用 | 互斥重建 / 热点不过期 | 入口校验 + 空值缓存 + 布隆过滤器 |

### 雪崩：两种诱因分开治

- **同时过期**：①TTL 加随机值打散；②互斥锁——同一时间只放一个请求去查库重建，其余等待或返回默认值（**锁必须带超时**，防重建线程挂掉后全局卡死）；③缓存不过期 + 后台定时更新（失效检测要毫秒级，或用消息队列通知后台补），配合上线前**缓存预热**。
- **Redis 宕机**：①熔断（暂停缓存访问，直接返回错误保数据库）或限流（只放少量请求到库）；②根治靠高可用架构（主从 + [[redis-cluster|哨兵/Cluster]]）。

### 穿透：布隆过滤器原理

位图数组 + N 个哈希函数：写入时 N 个哈希位置 1；查询时任一位为 0 → **必不存在**；全 1 → 可能存在（哈希冲突）。Redis 原生支持。另两道防线：API 入口参数合法性校验（拦恶意请求）、缓存空值/默认值（配短 TTL）。
