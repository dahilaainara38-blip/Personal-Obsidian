# Redis 持久化

> 在内存数据库上做持久化的核心矛盾是：**单线程命令执行不能被磁盘 I/O 阻塞**。Redis 的解法是 fork 子进程 + 写时复制，把落盘这件事整个挪出主进程。

## 核心要点

- 四种选择：**无持久化 / RDB / AOF / RDB+AOF 混合**。选哪个取决于"能丢多少数据"和"重启要多快"。
- **RDB = 时间点快照**：紧凑、加载快，但两次快照之间的数据会丢；`fork` 在数据集大时会造成瞬间延迟。
- **AOF = 追加写命令日志**：更持久（配合 fsync），文件更大、不紧凑，重启时重放重建数据。
- **两者同开时，重启用 AOF 重建** —— 因为它最完整。这是"鱼与熊掌兼得"的推荐配置，代价是磁盘与写放大。
- **底层机制 fork + COW 是理解 Redis 持久化的钥匙**：子进程共享父进程内存页，只有被修改的页才真正复制，所以能低成本拿到快照。

## 细节

### 三种方式对照

| 方式 | 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 无持久化 | 不落盘 | 最快，无持久化开销 | 重启即失 | 纯缓存，数据可重建 |
| RDB | 定时 fork 生成内存快照 | 文件紧凑、重启加载快、便于备份传输 | 快照间数据会丢；大数据集 fork 有延迟尖刺 | 可容忍分钟级丢失、需要快速恢复 |
| AOF | 追加记录每条写命令 | 数据最完整、可读可审计 | 文件大、恢复慢、写放大 | 不能接受丢数据 |
| RDB+AOF | 两者同开 | 兼顾完整性与加载速度 | 磁盘占用与写放大 | 生产常见选择 |

### fork + 写时复制（COW）怎么工作

1. 主进程 `fork` 出子进程，二者**共享同一份内存页**（不是复制一份）
2. 子进程把这份"冻结"的内存视图写盘，主进程继续正常服务
3. 若期间主进程修改了某个内存页，内核才把该页复制一份给修改方 —— **只复制被改动的页**
4. 于是：用极小的额外内存，拿到了数千 GB 级内存的时间点快照

关键点：**快照期间如果没有任何写入，就完全不发生内存复制** —— 这是 COW 的精髓。详见 [[copy-on-write]]。

### 一个容易忽略的取舍

持久化不是免费的。**所有 Redis 复制都是异步的**，意味着：
- 主库写入成功 ≠ 从库已收到
- 主库宕机时，未同步的写入会永久丢失
- 若要缓解，可强制要求至少一个副本确认后主库才接受写入 —— 但这拿**可用性**换**一致性**，主库会被慢副本拖住

这个"异步复制必然丢数据"的事实，是理解 [[redis-cluster]] 里 Sentinel 风险的钥匙。

## 疑点与待验证

- RDB 的 `fork` 延迟尖刺在多大实例上会变得不可接受？缺具体量级数据（经验值常提 GB 级，未验证）
- AOF 的 fsync 策略（always / everysec / no）本文只笼统提到"如果可能则 fsync"，三档的具体语义与数据安全级别待查
- Redis 4.0+ 的"混合持久化"（AOF 里含 RDB 前导）本文未提，是现代 Redis 的重要特性，待补充
- 本文未涉及 AOF rewrite 机制 —— AOF 文件如何避免无限增长？待查
