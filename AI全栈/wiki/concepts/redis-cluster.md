# Redis 高可用与集群

> 从单实例到 Cluster 是一条"每一步都在用复杂度换能力"的阶梯。理解它的关键是：**复制是异步的**，这一条决定了后面所有风险。

## 核心要点

- 四档形态：**单实例 → 主从复制 → Sentinel → Cluster**，分别解决"跑起来"、"读扩展/冗余"、"自动故障转移"、"水平扩容"。
- **复制靠「复制 ID + 偏移量」识别血缘**：ID 相同且只差少量偏移 → 部分同步；ID 不同 → 全量同步（代价高）。主实例被提升时会**记住旧的复制 ID**，这是故障转移后仍能部分同步的关键设计。
- **Sentinel 既是故障检测器，也是服务发现**（类似 Zookeeper / Consul 的角色），客户端通过它问"现在谁是主库"。
- **Sentinel 的硬伤是异步复制导致的丢数据**：旧主库在少数派分区里的写入，恢复后会被丢弃。
- **Cluster 用 16384 个哈希槽解决分片**，扩缩容只搬槽不搬 key。详见 [[data-sharding]]

## 细节

### 四档形态对照

| 形态 | 解决什么 | 代价 |
|---|---|---|
| 单实例 | 简单、快 | 实例挂了全挂，无 HA |
| 主从复制 | 读扩展、数据冗余 | 主库故障需人工切换 |
| Sentinel | 自动故障转移 + 服务发现 | 异步复制会丢数据；部署有讲究 |
| Cluster | 突破单机内存上限，水平分片 | 运维复杂度显著上升、脑裂风险 |

### 复制：部分同步 vs 全量同步

- 每个主实例持有**复制 ID** 和**偏移量**，每个写操作让偏移量递增
- 副本落后少量偏移 → 主库补发缺失命令，副本重放即可（**部分同步**，便宜）
- 复制 ID 不一致或主库不认识该偏移量 → **全量同步**：主库生成新 RDB 传给副本（昂贵）
- 全量同步期间，主库会**缓冲快照期间的增量命令**，快照传完再补发，保证不断流
- **关键设计**：实例被提升为主库时会获得新复制 ID，但**记住旧的 ID** —— 这样其他副本仍能据此推断共同祖先，走部分同步，避免故障转移引发全量同步风暴

### Sentinel 的三条实践结论

1. **至少 3 个哨兵节点，quorum 至少 2。** 对照表：

   | 节点数 | Quorum | 可容忍故障数 |
   |---|---|---|
   | 1 | 1 | 0 |
   | 3 | 2 | 1 |
   | 5 | 3 | 2 |
   | 7 | 4 | 3 |

2. **哨兵节点尽量与应用服务器同机部署** —— 避免哨兵与客户端的网络拓扑错位，导致哨兵看到的主库和客户端连的不一致。
3. **Sentinel 的三个必翻的车**（跑久了都会遇到）：
   - 哨兵节点数跌破法定人数 → 丧失故障转移能力
   - 网络分裂把旧主库隔离到少数派 → 那些写入在恢复后**全部丢失**
   - 哨兵与客户端网络拓扑错位 → 客户端连错节点

   缓解手段：要求至少一个副本确认写入，主库才接受写 —— 但这会牺牲可用性。

### Cluster 与脑裂

- 节点间通过 **Gossip 协议**交换健康信息
- 足够多节点认为 M1 无响应 → 把它的副本 S1 提升为主
- **脑裂（split-brain）**：网络分区两侧各自达成 quorum，集群被撕成两半
- 防范的一般规则：**奇数个主节点 + 每个主节点两个副本**
- 触发提升所需的节点数是可配的，配错了（两侧都能达成）就会脑裂

## 疑点与待验证

- 客户端如何感知主库切换？本文只说"建立新连接时查询新主节点"，具体客户端（Jedis / Lettuce / Redisson）的重连与拓扑刷新机制待查
- Cluster 的 MOVED / ASK 重定向细节、以及客户端缓存槽位映射的机制，本文未涉及
- "奇数个主节点 + 两个副本"是经验规则，其背后的严格推导（为什么 2 副本）未给
- 脑裂的具体判定与恢复流程，本文只给了概念，缺实操
