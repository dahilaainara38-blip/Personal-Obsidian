# 数据库与缓存一致性（双写一致性）

> 缓存与数据库是两个独立存储，写操作必有先后——**默认解是 Cache Aside「先更新数据库，再删除缓存」+ 过期时间兜底**，删除失败靠 MQ 重试或 Canal 订阅 binlog 补偿。

## 核心要点

- **任何"更新缓存"的顺序都躲不过并发写错序**——两个写请求交错时，缓存最终值可能取自先到的旧请求。
- **"删除缓存"优于"更新缓存"**：删除更轻、出错面小；缓存值常是多表聚合，更新代价大；且更新后未必被读（Lazy Loading）。
- **先删缓存再更 DB 也不行**：读请求会在"删后更前"窗口把旧值回填。
- **先更 DB 再删缓存**理论上有窗口（读请求查到旧值、回填晚于写请求的删除），但**缓存写入远快于 DB 写入，实际概率极低**，加 TTL 即最终一致——这是工程默认答案。
- 强一致是伪命题：除非串行化所有读写（代价不可接受），否则只能做到**最终一致**。

## 细节

### 四种方案对照

| 方案 | 一致性 | 复杂度 | 适用 |
|---|---|---|---|
| 先更 DB 再删缓存 + TTL | 最终一致（窗口极小） | 低 | **默认选择** |
| 延迟双删（删→更→sleep→再删） | 尽可能一致 | 中（sleep 时长玄学） | 存量"先删"系统改造 |
| 更 DB + MQ 重试删缓存 | 删除必成功 | 中（代码侵入） | 删除失败敏感 |
| 更 DB + Canal 订阅 binlog → MQ → 删 | 删除必成功且零侵入 | 高（组件多） | 大型系统 |

### 删除失败补偿的关键细节

- **Canal 伪装成 MySQL 从库**拉 binlog，解析后发 MQ，消费者删缓存——业务代码零耦合。
- **必须先删缓存成功、再回 ACK 给 MQ**，否则提前 ACK 后删除失败就永久丢消息。
- 读路径回填缓存 与 [[cache-pitfalls]] 的互斥重建是同一处代码：回填时加锁/随机退避，防止击穿式并发回填。

### 例外：高命中率需求

对命中率敏感的业务可用"更 DB + 更缓存"，但需 **[[distributed-lock|分布式锁]]串行化** 或 配**短 TTL** 接受短暂不一致。

## 疑点与待验证

- "先更 DB 再删缓存"的不一致窗口，在**读放大极高**（回填耗时长）的场景是否仍然够小？缺乏实测数据
- Canal 方案的延迟量级（binlog → 删缓存）与 MQ 选型待实践
- Java 侧：Spring Cache 的 @CacheEvict 即"删缓存"语义，与手动方案的事务边界问题（DB 提交后才应删）待验证
