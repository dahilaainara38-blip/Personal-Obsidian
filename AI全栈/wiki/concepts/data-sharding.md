# 数据分片

> 当数据装不进一台机器时，如何把它摊到多台机器上 —— 以及**更难的：加机器的时候怎么少搬数据**。

## 核心要点

- 分片要回答两个问题：**key 去哪台机器**（路由），和**加机器时搬多少数据**（再平衡）。
- **朴素取模分片的致命伤**：`hash(key) % N`，N 一变，几乎所有 key 的映射都漂移，等于全量重搬。
- **Redis Cluster 的解法是加一层间接：哈希槽。** key 先映射到固定 16384 个槽（`CRC16(key) % 16384`），槽再映射到实例。**key→槽固定不变，只有槽→实例会变**，所以扩缩容只需搬槽。
- 这个"**加一层间接层解决映射漂移**"的思路，是分布式系统里的通用手法，不只在 Redis 里出现。
- 分片的隐藏成本：**跨分片操作变难**（多 key 事务、聚合、join 都受限于 key 是否同槽）。

## 细节

### 为什么朴素取模不行

```
3 个分片：foo → hash % 3 = 0  → M1
加 1 个分片：foo → hash % 4 = ?  → 大概率变了
```

N 从 3 变 4，绝大多数 key 的归属都会变。要扩容就得搬几乎全部数据，**慢、不现实、还影响可用性**。

### 哈希槽怎么解决

```
key → CRC16(key) % 16384 → 槽（固定 16384 个，永不改变）
槽 → 实例（可变，扩缩容时迁移）
```

举例：
- 初始：M1 持槽 0–8191，M2 持槽 8192–16383
- 加入 M3 后：M1 持 0–5460，M2 持 5461–10922，M3 持 10923–16383
- 只需把 M1、M2 各自的一部分槽**整体搬给 M3**，槽内的 key 无需重新计算哈希

**所以"误导（misdirection）"这一层间接，把重新分片的成本从"所有 key"降到了"部分槽"。** 且可做到无停机、性能影响最小。

### 三种方案对照

| 方案 | 扩容时搬多少 | 复杂度 | 典型使用者 |
|---|---|---|---|
| 取模分片 | 几乎全部数据 | 低 | 简易自研 |
| **哈希槽** | 部分槽 | 中 | Redis Cluster |
| 一致性哈希 | 约 1/N | 中（含虚拟节点） | 多种分布式缓存/存储 |

> ⚠️ **一致性哈希不在本知识库当前素材范围内。** 上表中它的描述属于外部常识补充，**未经素材验证**，若要用请自行核实。（一致性哈希是 [[redis-cluster]] 未采用的另一条路线，值得单独收录素材对比。）

## 疑点与待验证

- **为什么是 16384 这个数？** 本文只给了结论没给理由。常见解释与集群心跳包大小、槽位位图开销有关 —— **待查证，勿引用未核实的说法。**
- 一致性哈希与哈希槽的正式对比，需要单独素材支撑
- 跨分片操作（多 key 事务、Lua）在哈希槽模型下如何约束？本文未涉及
- 热点 key 问题：某个槽特别热怎么办？分片方案本身不解决，需要额外的本地缓存或 key 拆分
