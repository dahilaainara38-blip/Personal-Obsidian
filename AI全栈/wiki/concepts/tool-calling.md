# Tool Calling（工具调用 / Function Calling）

> 让模型不直接回答，而是输出"我要调用哪个函数、传什么参数"，由你的代码真正执行，再把结果喂回模型。模型负责**决策**，你的代码负责**执行**。

## 核心要点

- 这是模型从"聊天"跨到"做事"的关键一步，也是 [[agent]] 的基础设施。
- **模型永远不直接执行代码**，它只产出结构化的调用意图。真正执行的永远是你的程序 —— 这个边界是安全性的根基。
- 工具描述的**质量决定调用准确率**。描述写得含糊，模型要么不调，要么乱调。
- 参数用 **JSON Schema** 声明，字段描述比字段名更重要。
- 生产要点：幂等、超时、鉴权、审计日志，一个都不能少。

## 细节

### 一次完整的调用循环

1. 你的代码把「工具定义（名字+描述+参数 schema）」连同用户问题发给模型
2. 模型返回 `tool_calls`：函数名 + 参数（或返回普通回答，表示不需要工具）
3. 你的代码**校验参数** → 执行真实逻辑 → 得到结果
4. 结果作为 tool message 追加回消息列表，再次请求模型
5. 模型基于结果生成最终回答（或再次要求调工具，形成循环）

### 写好工具定义的三条规则

- **名字用动词短语**：`query_order_by_id` 优于 `order`
- **描述说清"什么时候该用、什么时候不该用"**，不只是"它能做什么"
- **每个参数都写 description**，并给出枚举值或示例；区分必填与选填

### 常见坑

| 坑 | 现象 | 对策 |
|---|---|---|
| 工具太多 | 模型选错或瞎选 | 按场景动态挂载，控制在 10 个以内 |
| 参数编造 | 模型编出不存在的 ID | 执行前校验，失败时把错误回传给模型让它改 |
| 死循环 | 反复调同一个工具 | 设最大轮次，触发后强制总结退出 |
| 副作用不可控 | 重复下单 | 幂等键 + 高风险操作走 HITL 人工确认 |
| 不调工具 | 模型自己硬答 | 检查描述是否清楚；必要时提高 tool_choice 约束 |

### Java 侧实现位置

- Spring AI：`@Tool` 注解 + `ToolCallbackProvider` + `ChatClient.toolCallbacks(...)`，支持 `ToolContext` 透传上下文（如当前用户）
- LangChain4j：`@Tool` 注解 + `AiServices`，支持返回类型自动序列化
- 跨进程供给：[[mcp]]
