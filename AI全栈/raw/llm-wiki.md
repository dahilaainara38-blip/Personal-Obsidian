# LLM Wiki

A pattern for building personal knowledge bases using LLMs.

这是一份 idea file，设计目标是复制粘贴给你自己的 LLM Agent（OpenAI Codex、Claude Code、OpenCode / Pi 等），用来传达高层理念，具体细节由你的 agent 与你协作落地。

## The core idea

大多数人与 LLM + 文档的交互方式是 RAG：上传一批文件，LLM 在提问时检索相关片段，生成答案。这能用，但**每次提问都在从零重新发现知识**，没有积累。问一个需要综合五份文档的微妙问题，LLM 每次都得重新找齐并拼装片段。**什么都没沉淀下来。** NotebookLM、ChatGPT 文件上传、以及大多数 RAG 系统都是这个模式。

这里的思路不同。与其在查询时从原始文档检索，不如让 LLM **增量地构建并维护一个持久化的 wiki** —— 一个结构化的、互相链接的 markdown 文件集合，位于你和原始素材之间。当你加入新素材时，LLM 不只是索引它以备后用，而是阅读它、抽取关键信息、并把它整合进已有的 wiki —— 更新实体页、修订主题摘要、指出新数据与旧结论矛盾的地方、强化或挑战正在演进的综合判断。**知识被编译一次，然后持续保持最新，而不是每次查询重新推导。**

关键区别：**wiki 是一个持久的、复利的产物。** 交叉引用已经在了，矛盾已经被标记了，综合判断已经反映了你读过的所有东西。每加一份素材、每问一个问题，wiki 都在变厚。

你几乎从不自己写 wiki —— LLM 写并维护全部内容。你负责选源、探索、问对问题。LLM 干所有苦力活 —— 摘要、交叉引用、归档、以及那些让知识库长期有用的账面工作。实践中，我一边开着 LLM agent，一边开着 Obsidian。LLM 基于我们的对话做编辑，我实时浏览结果 —— 点链接、看图谱视图、读更新后的页面。**Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。**

适用场景举例：

- **个人**：追踪自己的目标、健康、心理、自我提升 —— 归档日记、文章、播客笔记，随时间构建对自己的结构化认知。
- **研究**：数周或数月深入一个主题 —— 读论文、文章、报告，增量构建一个带演进论点的综合 wiki。
- **读书**：边读边归档每一章，为人物、主题、情节线建立页面及其连接。读完后你就有了一个丰富的 companion wiki。想想 Tolkien Gateway 这样的粉丝 wiki —— 数千个互链页面，由志愿者社区耗时数年建成。你可以在自己阅读时个人化地建一个类似的东西，由 LLM 承担全部交叉引用和维护工作。
- **商业/团队**：由 LLM 维护的内部 wiki，输入来自 Slack 讨论串、会议转录、项目文档、客户电话，可能有人工审核环节。wiki 保持最新，因为 LLM 承担了团队里没人愿意做的维护工作。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深挖** —— 任何你随时间积累知识并希望它被组织起来而非散落各处的场景。

## Architecture

三层：

**Raw sources** — 你精选的源文档集合。文章、论文、图片、数据文件。这些是**不可变的** —— LLM 读取但永不修改。这是你的真相来源。

**The wiki** — 由 LLM 生成的 markdown 文件目录。摘要、实体页、概念页、对比、总览、综合。LLM 完全拥有这一层。它创建页面，在新素材到来时更新，维护交叉引用，保持一切一致。你读它；LLM 写它。

**The schema** — 一份文档（如 Claude Code 的 CLAUDE.md，或 Codex 的 AGENTS.md），告诉 LLM wiki 如何组织、约定是什么、以及在收录素材、回答问题、维护 wiki 时该遵循什么工作流。**这是关键的配置文件** —— 它让 LLM 成为一个有纪律的 wiki 维护者，而不是一个泛泛的聊天机器人。你和 LLM 随着摸清什么适合你的领域，共同演进它。

## Operations

**Ingest.** 你把新素材丢进 raw 集合，让 LLM 处理它。示例流程：LLM 读素材，与你讨论关键要点，在 wiki 里写一个摘要页，更新索引，更新全 wiki 相关的实体页与概念页，并向日志追加一条。**一份素材可能触及 10-15 个 wiki 页面。** 我个人偏好一次收录一份并保持介入 —— 我读摘要、检查更新、指导 LLM 该强调什么。但你也可以低监督地批量收录多个素材。由你来发展出适合你风格的工作流，并把它写进 schema 供后续会话使用。

**Query.** 你针对 wiki 提问。LLM 搜索相关页面，阅读它们，综合出带引用的答案。答案可以有不同的形式 —— 一个 markdown 页面、一张对比表、一份幻灯片（Marp）、一张图表（matplotlib）、一块画布。**重要洞察：好的答案可以被归档回 wiki 成为新页面。** 你问的对比、做的分析、发现的连接 —— 这些是有价值的，不该消失在聊天记录里。这样你的探索就像收录素材一样在知识库里复利。

**Lint.** 定期让 LLM 给 wiki 做健康检查。检查项：页面之间的矛盾、被新素材取代的过时论断、没有入链的孤儿页、被反复提及却缺少独立页面的重要概念、缺失的交叉引用、可以通过联网搜索填补的数据空白。LLM 很擅长提出值得研究的新问题和值得找的新素材。这让 wiki 在成长中保持健康。

## Indexing and logging

两个特殊文件帮助 LLM（和你）在 wiki 成长时导航。它们用途不同：

**index.md** 是面向内容的。它是 wiki 里所有东西的目录 —— 每个页面带链接、一行摘要，以及可选的元数据（日期、来源数）。按类别组织（实体、概念、来源等）。LLM 每次收录时更新它。回答查询时，LLM 先读索引找到相关页面，再下钻进去。**在中等规模（约 100 份素材、数百个页面）下这效果好得出人意料**，并且避免了需要 embedding 的 RAG 基础设施。

**log.md** 是时间序的。它是"发生了什么、什么时候"的 append-only 记录 —— 收录、查询、lint 轮次。一个有用的技巧：如果每条都以固定前缀开头（例如 `## [2026-04-02] ingest | Article Title`），日志就能用简单的 unix 工具解析 —— `grep "^## " log.md | tail -5` 给你最近 5 条。日志给你 wiki 演进的时间线，也帮 LLM 理解最近做了什么。

## Optional: CLI tools

某个时候你可能想构建一些帮助 LLM 更高效操作 wiki 的小工具。最明显的是 wiki 页面的搜索引擎 —— 小规模时索引文件就够了，但随着 wiki 增长你会想要正经的搜索。qmd 是个好选择：一个本地 markdown 搜索引擎，混合 BM25/向量搜索 + LLM 重排，全部在本机。它既有 CLI（LLM 可以 shell 调用），也有 MCP server（LLM 可以当原生工具用）。你也可以自己搭个更简单的 —— 需要时让 LLM 帮你 vibe code 一个朴素搜索脚本。

## Tips and tricks

- **Obsidian Web Clipper** 浏览器插件，把网页文章转成 markdown。对快速把素材弄进 raw 集合非常有用。
- **把图片下载到本地。** Obsidian 设置 → 文件与链接，把"附件文件夹路径"设为固定目录（如 `raw/assets/`）。然后在设置 → 快捷键里搜 "Download"，找到"下载当前文件的附件"，绑一个快捷键（如 Ctrl+Shift+D）。剪藏完一篇文章，按快捷键，所有图片就下到本地磁盘了。这可选但有用 —— 让 LLM 能直接查看和引用图片，而不依赖可能失效的 URL。注意 LLM 没法一次读完带内联图片的 markdown —— 变通做法是让 LLM 先读文本，再单独查看部分或全部被引用图片以获得额外上下文。有点笨但够用。
- **Obsidian 的图谱视图** 是看 wiki 形状的最好方式 —— 什么和什么连着、哪些页面是枢纽、哪些是孤儿。
- **Marp** 是基于 markdown 的幻灯片格式。Obsidian 有插件。对直接从 wiki 内容生成演示很有用。
- **Dataview** 是一个对页面 frontmatter 跑查询的 Obsidian 插件。如果你的 LLM 给 wiki 页面加了 YAML frontmatter（标签、日期、来源数），Dataview 能生成动态表格和列表。
- wiki 只是一个 markdown 文件的 git 仓库。你免费获得版本历史、分支和协作。

## Why this works

维护知识库繁琐的部分不是阅读或思考 —— 是**账面工作**。更新交叉引用、保持摘要最新、记录新数据与旧论断矛盾之处、在几十个页面间维持一致性。人类放弃 wiki，是因为维护负担增长得比价值快。LLM 不会厌烦，不会忘记更新交叉引用，能一次触及 15 个文件。wiki 得以被维护，因为维护成本近乎为零。

人的工作是精选素材、引导分析、问好问题、思考这一切意味着什么。LLM 的工作是其他一切。

这个想法在精神上接近 Vannevar Bush 的 Memex（1945）—— 一个私人的、精选的知识库，文档之间有关联路径。Bush 的愿景比后来诞生的 web 更接近这个：私密的、主动精选的、文档之间的连接与文档本身同样有价值。他没能解决的是**谁来做维护**。LLM 解决了。

## Note

本文档刻意保持抽象。它描述的是想法，不是某个具体实现。确切的目录结构、schema 约定、页面格式、工具链 —— 这些都取决于你的领域、你的偏好、你选的 LLM。上面提到的一切都是可选和可插拔的 —— 挑有用的，忽略没用的。例如：你的素材可能纯文本，那就完全不需要图片处理。你的 wiki 可能小到索引文件就够了，不需要搜索引擎。你可能不在乎幻灯片，只想要 markdown 页面。你可能想要完全不同的一组输出格式。正确的用法是把它分享给你的 LLM agent，然后一起实例化出一个适合你需求的版本。本文档唯一的职责是传达这个模式。剩下的你的 LLM 能搞定。
